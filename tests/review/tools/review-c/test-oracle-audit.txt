This audit was made separately from reading the implementation. Sources below
are docs/design/host-concurrency.md (D) and docs/spec.md (S) on this worktree.
T numbers refer to D section 10.2. JS equivalents have the same source unless

Source sentences used by the decisive expectations

T1 many_requests_complete_out_of_order
  h == fold(completed): D H5 says the in-repo hosts "answer in completion
  order". D 8.1 says the fixture folds h=(h*31+k+1) mod (2^31-1) in answer
  order. S B.5 alone permits any answer order; completion order is the
  stronger accepted host implementation requirement in D, not a language rule.
  starts == drops == 2n, no unfinished drops: D 8.1 says it starts one more
  request after each of the first n answers until 2n requests are answered;
  D 10.1 says all drops = starts once everything is dropped.
  second call succeeds/reuses ids: S B.4 says an id may be reused after an
  answer/cancel/drop. No fault has occurred, so permanent refusal is unwarranted.
  JS answered signals not aborted: D 7 explicitly says an answered request is
  removed before delivery, so "an answered request is never aborted".
  JS no live allocations: S B.3 requires the receiver to free result buffers.
  Both 200-seed tests fail an ordering mutation; see the mutation logs.

T2 timers_answer_through_the_reactor
  order == [8,7,...,1], h == fold(order): D 10.1 sets timer delay to n+1-x,
  and D H5 requires completion order. D 10.2 T2 explicitly requires paused
  time and reverse order (written in zero-based request indices there).
  The repeat count 200 is specified by D T2, not by the language spec.

T3 a_stop_drops_outstanding_requests
  stop text "fixture: stop": D 8.1 describes that literal fixture stop.
  starts/drops/unfinished == 3/3/2: D 8.1 says stop_mid starts three and
  traps on the first answer; D H8 says drop all outstanding work before
  reporting the outcome. S B.5 says no further use after a trap.
  JS: two aborted signals before rejection comes from the same rules plus
  D 7's requirement to abort dropped work.

T4 a_host_failure_drops_the_others
  returned failure and unusable instance: S B.5 says "When the work of an
  async function fails in the host ... the host drops every outstanding
  request and does not use the instance again."
  drops == starts == 5 and unfinished == 5-completed: D 8.1 fan starts n
  requests with no replenishment; D 10.1 explains completed-future drops.
  "the gate failed" is the deliberately injected failure, not a required
  diagnostic string of the language. Returning that error is D H9's rule.

T5 status_one_with_nothing_outstanding_is_a_fault
  fault/unusable and exact no-host-function text: S B.5 says status 1 with
  nothing outstanding is a fault and the host does not use the instance
  again. D H4 explicitly supplies "the module waits, but no host function
  is running".

T6 duplicate_or_negative_id_traps
  duplicate starts == 1, negative starts == 0: D H2 says both hosts check
  BEFORE calling the service, so a refused request never runs its service.
  D H1 and S B.4 require nonnegative, unique outstanding ids.
  D 5.4 gives the exact duplicate/negative diagnostic strings.
  drops == starts follows H8 and the fact that these starts never complete.

T7 a_sync_call_may_not_start_requests
  sync/start/nested-allocator/result admission failures and start counts:
  S B.4 permits requests only during async entry/resume/continue and not
  during another import. D H2 explicitly includes start, result, nested
  allocator, and cancel, and says refusals must precede service execution.
  Preserve the inner diagnostic: D H2 says "The error text is the first
  failure of the call" and explains the nested-allocator case.
  Exact outside-an-async-call strings are specified in D 5.4 and H13.
  A nested cancel/result failure can have one earlier legitimate start;
  these are described in D 8.1. No assertion was inferred merely from code.

T8 leftovers_are_dropped_at_status_zero
  3 starts, 3 drops, 2 unfinished, one answer contributing to h: D 8.1 says
  leftover starts three and returns 0 on the first answer. S B.5 explicitly
  requires dropping leftovers at 0. D H7 says this is normal termination.
  Instance usable and next call succeeds: D T8 states that expectation and
  H7 requires both tables empty before the next entry.

T9 a_wrong_resume_traps; compiled.test.mjs raw resume assertions
  unknown, answered/stale, and wrong-import ids trap: S B.5 says "A call of
  ilang_resume:... with an id that is not outstanding, or that another
  function started, traps." Bare unreachable/no stop message: D H6 says so.
  Counter starts at 0, then increments: D H1 specifies the C compiler's
  counter starting at 0 and wrapping at 2^31.
  The successful continuation after these traps in compiled.test.mjs:51
  is NOT specified; it conflicts with S B.5's no-use-after-trap rule.

T10 dropping_a_waiting_call_makes_the_instance_unusable
  After one poll: three starts, zero drops. On drop: three drops, all
  unfinished, immediately while the Instance still exists. D H11 says
  dropping the call future immediately drops its requests and gives the
  exact unusable text "an async call was dropped while it waited".
  D 8.1 many(3) supplies the three requests; held work cannot complete.

T11 deep_recursion_after_a_resume_stops_like_a_sync_call
  moderate recursion succeeds; deep recursion has identical trap/no message
  on fallback, fast path, and resume: D D5 and 5.6 explicitly preserve
  WASM_STACK/THREAD_STACK and stack/stop behaviour; D T11 demands equal
  trap texts. The particular moderate value 100000 is a chosen test input,
  not a promised universal recursion depth. "call stack exhausted" is
  the host regression requirement of D 5.6/T11, not portable ABI wording.

T12 block_on_works_inside_a_tokio_runtime
  no deadlock/panic: D D5 says block_on starts its own runtime/thread and
  works within the caller's Tokio runtime.
  Values 2.5, 4, and 6: D 8.1 retains the fixture's two later calls and
  first-answer-plus-one convention; these are fixture arithmetic.
  Fallback timers work and order [4,3,2,1]: D D5 says capture the caller's
  Tokio Handle BEFORE spawning the fallback thread; D 10.1 supplies
  n+1-x timer delays; H5 supplies completion order.

T13 old_and_new_versions_are_refused
  Versions 1/2 require rebuild; 4 requires updating host; 3 accepted:
  S B.6 requires version 3 and rejection of every other version.
  D D9 supplies both exact diagnostic strings.

T14 run_entry_uses_one_thread
  Four print calls, three service starts per run: D 8.1 one-thread fixture
  prints initially and after each of three answers.
  All ids equal and different from caller's: D D5 says one new ilang thread
  per program or test, including instantiate/start. D T14 explicitly
  requires the recorded print and start ids to match.
  Each run/test succeeds; one report: fixture's entry/test contract and
  S 10.2's each-test-in-a-new-instance rule.

T15 futures_are_send
  Compile-time Send checks for run/call futures, ServiceFuture, Value,
  Outcome, TestResult: D D5 explains the Send breaking change; D T15
  explicitly names these checks. Instance: Send is an additional useful
  compile-time implementation assertion, not an explicit ABI requirement.

T16 a_sync_service_may_block_on_its_own_thread
  Own-thread variant succeeds; nested Runtime::block_on panics with Tokio's
  message: D D5 documents both alternatives and this breaking change;
  D T16 explicitly requires both observations.

T17 cancel_drops_one_request
  n starts/drops, floor(n/2) cancelled, remaining answers contribute to h:
  D 8.1 cancel fixture cancels the lowest outstanding id after each answer.
  Drop timestamps [1,...,floor(n/2)] and no later cancelled answer:
  D H13 requires immediate drop, including a ready answer; D 5.4 explicitly
  requires the future dropped before the resume that cancels it returns.
  Bad-cancel failure and exact text: S B.4 requires trap/unusable for a
  non-outstanding id; D H13 provides the literal diagnostic.
  JS corresponding abort counts/timing are specified by D 7 and 10.3.

T18 status_two_gives_ready_answers
  Count >=1 and <m, ready work delivered, timer fires: S B.5 requires a
  nonblocking host-work turn and delivery of a ready answer before continue.
  D 8.1 says the fixture's resume returns 2, then continue ends it and counts
  its calls; hence at least one continue is required even for ready work.
  D T18 explicitly chooses m=1000 (ready), 10^7 (real timer), and bounds.
  No absolute number of scheduling turns is specified.

T19 every_return_from_wait_drops_the_requests
  HOST_VALUE_REASON, unusable has that text rather than H11's dropped-call
  text, 3 drops/2 unfinished: S B.2 specifies the host-value stop;
  D H11a explicitly includes lower_reply's wrong-value return and requires
  preserving its outcome while dropping remaining work. D T19 specifies
  the three-request experiment. JS late resolves must have no effect:
  D 7 requires identity-checked settlements and ignoring dropped requests.

T20 cancel_and_reuse_with_a_finished_answer
  h matches completion/delivery order, no stale value accepted, all futures
  dropped: D H1/H13 permit immediate reuse and prohibit answering cancelled
  work; D 8.1 explains changing expected argument for the reused id.
  dropped_released > 0 across seeds: D 10.1 requires this coverage check
  for the burst switch, so cancellation actually reaches ready work.
  In Rust, "released" means externally ready but not necessarily polled
  to Ready yet; it is not proof of a separately buffered Rust reply.

T21 requests_from_ilang_continue
  n starts, n-1 answers, one cancelled argument-0 future, h over answered
  requests: D 8.1 continue_io starts nothing initially, starts one per
  continue, cancels the first in the second continue; D 10.1 holds x=0.
  Admission from continue: S B.4 expressly permits it. D H14 allows status
  2 with no outstanding requests. Cancellation follows H13.

T22 bad_statuses_are_faults
  Status 7 fault/unusable: S B.5 says every status except 0/1/2 is a fault.
  Exact Rust "Some(7)" formatting is implementation-derived; D H4 gives
  different illustrative formatting and does not require Some(...).
  Missing continue/resume fault and no later sync execution: S B.5's two
  missing-export sentences; D H5/H14 give exact missing-export messages.
  Reserved metadata rejection: S B.5 explicitly reserves ilang_continue.
  Raw continue after status 1 traps: D H14 explicitly says the fixture traps
  at that time; S B.5 calls that host behaviour instance-breaking.
  JS host.test.mjs:581 nevertheless requires successful continuation after
  the trap. That success value has no source and contradicts S B.5.

T23 a_finished_program_does_not_wait_for_blocking_work
  running == 2 before finish; <5 seconds; status-zero or stop outcome:
  D 5.2 requires shutdown_background rather than waiting for detached
  blocking work. D T23 explicitly demands already-running two 30-second
  blocking closures and an under-5-second return. These numeric bounds
  are design-specified test parameters, not latency promises in the ABI.

T24 a_nested_store_gets_its_own_thread
  Inner print id differs from outer; outer thread named ilang; deep inner
  call cleanly traps with the top-level stack-overflow text and no message:
  D D5 and 5.6 explicitly require a fresh native stack for nested stores.
  D T24 describes the print/deep sequence and these expected observations.
  Two callbacks in the additional allocator test come from its own WAT
  fixture (alloc and free each call touch). Different inner/outer ids are
  D5's same nested-store requirement, extended to allocator/free Wasm calls.

Other additions and JS/browser-specific expectations
  block_on_gives_services_tokio_io: successful bind/connect/accept comes
  from D D5's time-and-IO runtime contract. enable_all satisfies it when
  Tokio IO is enabled by feature unification; the dev dependency enables net.
  Wrong-type exports: S B.5 gives the resume type and explicit wrong-type
  fault; continue() -> i32 gives its required type. D H5/H14 require faults.
  calls()==0 verifies the bad export/sync call never ran (D H10).
  Abort of the failed/malformed-answer request itself is not required after
  it was removed for delivery; D 7 only promises abortion of remaining work.
  Allocation trap tests: D H8/H11a explicitly include traps in ilang_alloc
  while preparing an answer; D H2 preserves the first nested-import failure.
  The literal "allocator stop" comes from the test's WAT panic data, not
  the language; preserving it is H8's existing outcome-shape requirement.
  Countdown h/order and length 2n: D 10.1 says countdown order depends on
  FuturesUnordered and only equality with the observed order is checked;
  D 8.1 defines the 2n fixture requests.
  Self-waking ready() poll count exactly 1: implementation-specific
  regression invariant. H14 requires returning without waiting and reactor
  progress, but neither S nor D requires precisely one inner poll.
  Self-waking timer order [1,0]: test work defines that work 1 sets the flag
  needed by work 0; H14/D5 provide progress, fixture logic provides the order.
  A JS service's mark is already set before callAsync yields: D D6 says
  fn is called synchronously during the import.
  JS re-entry refusals during imports and while waiting: S B.3 permits only
  alloc/free during imports; S B.5 permits only resume/continue/alloc/free
  while waiting/runnable. D 7 supplies depth/waiting guards and diagnostics.
  Re-entry attempts from abort listeners are refused: same H10/JS guard
  contract, with D 7 requiring synchronous abort during request drop.
  Default-parameter example result 8: D D6 says arguments are exactly the
  declared parameters, so scale retains its default; D 8.1 retains two calls
  with first result plus one: (1.5*2+1)*2=8.
  requestSignal outside service start or after await throws: D D6/7/10.3
  explicitly scopes it to service start and supplies the message.
  MessageChannel count <=1: an implementation resource-use regression
  assertion; S and D require a macrotask yield but do not impose a channel
  count. Timer-turn count >=2 in this particular test likewise is a chosen
  experimental check, not a specified scheduling count.
  Browser 200 seeds and 50-seed status2/cancel loops: D 10.4 explicitly
  specifies them. h/start-count/usability oracles have T1/T20/T21's sources.
  effects_keep_only_short_comments's <=6 consecutive comment lines:
  no S or D sentence imposes this threshold. It is a local style assertion.
  Compiled stop locations and metadata version: S 11.7 requires innermost
  source locations, D 8.2 names the unchanged source positions, S B.6/D D9
  require version 3. Float/Int malformed answer tests derive from S B.2.

Missing negative cases demonstrated by independent probes
  Both hosts accept status 2 with a ready request and no continue export,
  if its resume returns 0. S B.5 and D H14 unconditionally classify the
  missing continue export as a module fault when it gives status 2.
  Both accept start-work then immediate status 0 with no resume export.
  S B.5 and D H5 classify absence/wrong type of the started import's resume
  as a module fault, regardless of whether the host ultimately answers it.
  Existing tests cover missing exports only on the path that needs to invoke
  them; they therefore miss these two cases.
