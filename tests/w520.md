# W520: disjoint equality warnings

The accepted W520 instruction says: “the comparison type-checks, has type
`Bool`, and the checker reports a warning with a new W-code”. Spec §6.9
now says: “the two sides can never be equal” and “The warning adds no
narrowing fact.” W0503 follows W0501 (unused clause) and W0502 (unused
value). Literal types and disjointness are unchanged.

For a language user:

- Comparing known-disjoint values now compiles with W0503.
- `==` gives False and `!=` gives True, with type Bool.
- Literal types stay exact; no annotation or parameter wrapper is needed.
- An always-false clause guard still falls through to the next clause.
- `assert(1 == 2)` compiles and fails through Assert at run time.

- Elixir `lib/elixir/lib/module/types/apply.ex`: `do_remote` (equality),
  `compare`, `return_compare`, `custom_compare`, `remote_error`, and
  `format_diagnostic`; `helpers.ex`: `is_warning`, `error`,
  `effectively_warn`; `expr.ex`: `of_expr` for literals. Elixir warns on
  disjoint comparison outside inference, except two literal expressions
  and negative singleton refinements. Non-strict equality allows numeric
  coercion. Integer and binary literals have broad types; atoms can have
  singleton types. The helper named error collects a warning, marks the
  context failed, and the caller returns a gradual recovery type. Take the
  advisory diagnostic; leave the exemptions, coercion and recovery type.
  i equality is a general operator with type Bool, including constants.
- TypeScript `src/compiler/checker.ts`: `getFreshTypeOfLiteralType`,
  `getRegularTypeOfLiteralType`, `getWidenedLiteralType`,
  `getWidenedLiteralTypeForInitializer`,
  `getWidenedLiteralLikeTypeForContextualType`,
  `checkBinaryLikeExpressionWorker`, `reportOperatorErrorUnless`, and
  `tryGiveBetterPrimaryError`. The no-overlap diagnostic is an error;
  fresh mutable initializers and unconstrained returns can widen, while
  const, readonly and literal contexts keep precision. i takes neither
  freshness nor default widening: the accepted instruction says “keep
  literal types exactly as they are, with no widening”.

## Guards and fixtures

Spec §7.4 says: “A clause with a guard is not counted.” Thus both
`? x == 2` and `? x != 2` with `x: 1` leave coverage obligations.
`Checker::binary` still returns Bool and adds no subtype constraint
between operands. `Checker::case` still types the guard and body, and
records the presence of a guard, regardless of its constant result.
An invalid guarded body remains a type error. Coverage and narrowing
code need no change.

The four runtime fixtures restore only the comparison changes in
`86c9728` (T1). In blocks.i, the broad match subject introduced for W0501
stays. The restored values are required by spec §11.4: different integers
and strings are unequal; §6.9 makes their comparison legal with W0503.
The stop_tail_service fixture again infers its callback parameter, and
its stop is still required by Assert (§11.7) and the tail-call positions
(§§11.6–11.7).

`i check` prints W0503 to stderr and exits 0 when there are no errors.
`i test` prints build warnings to stderr before running tests; its exit
status follows test outcomes. The language server publishes W0503 with
Warning severity, both types, and the original comparison range.
These use the existing reporting paths and have integration tests.

The WAT dumper also exports fixtures with type-checker errors when it has
lowering data. WAT presence is not an acceptance check. The spec suite
and CLI checks establish acceptance separately.

report a warning, show the same two types at the same comparison span,
