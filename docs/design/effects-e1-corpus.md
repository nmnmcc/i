## Controlling paragraphs

- Spec §9.2, **Merging**: “The merge of two needs is their intersection (§4.4).”
- Spec §9.2: “When the intersection for one service of a need is `Never` while neither side is `Never`, the need cannot be satisfied: it is a compile error (E0515).”
- Spec §9.2: “A provided value of type `P` satisfies the need entry `S` when `P <: S` (§4.5 rule 4). An entry that every value of its type constructor satisfies, as `Fail(Never)`, is removed.”
- Spec §4.4: same-constructor intersections combine arguments by `&` for covariance, `|` for contravariance, and equality for invariance; “`a & T`, with a type variable `a`, stays as it is.”
- Syntax-three §2.10.4, Rule B: a written service handles its key; its remaining row lacks that key and retains the directed obligation.

## Compiler regressions fixed before recording

Deferred row meets stored variable operands in reverse inclusion links. Coalescing ignored those links and could turn the meet into `Top`, erasing required entry services. The fix preserves those operands. Both `review-k4d/_loose/p/r3` and `review-k4d/proj/r3` must still report E0523 for the unprovided `Dep`; `review-k4s/min_main_6_0` must still report E0523 for `S(Never)`. Their acceptance is not justified by E1. Spec §9.2 requires that service lookup never fail at run time.

The direct-forwarding copies `review-k4d/_loose/p/r2` and `review-k4d/proj/r2` also retain their `Dep` entry rejection. Proved row inclusions and aliases absorb redundant meets, so the `b8` copies do not acquire a false E0505 cycle; checking succeeds and entry execution still rejects with E0523. In `review-k4s/mixed_install_3`, the shared ordinary-value/need constraint still reports E0515 even though its test body independently reports E0501. A row used as an ordinary value retains its checked form in both directions; explicit provider satisfaction remains directed (§4.5 rule 4, §9.2). Every existing row-scheme assertion is unchanged.

All syntax-three fixtures previously failed through converted `i/failure.catch`: migration confused its ordinary `! Fail(E)` service with the transition lowerer’s bare `Fail(E)` shorthand for the legacy error channel. Migration now emits a transparent alias for the service, preserving its constructor and obligations. Spec §4.3: “`T = Type` is a transparent alias.” No syn3 expectation changed.

When that alias is beside a row variable, migration also marks an originally empty legacy error channel with `Fail(Never)`. This prevents the transition lowerer from inventing a separate error carrier for the row. Spec §9.2 removes this universal need entry, so it adds no service. A regression checks both the empty channel and preservation of an explicitly written legacy channel.
