# Rules the standard states that the compiler does not implement yet

State on 2026-11-14. Each rule below is specified in `docs/spec.md`; the compiler differs as described. This list is the
tracked difference between the definition and the implementation: an entry is removed by the commit that implements it.
The probes named here are kept outside the repository by the review that found them; each entry becomes a regression
case when it is implemented.

- **C03 — §9.9 R1 (with §9.4).** Rule now specified; today: a scope captured by user suspension remains in the caller’s chain; go succeeds outside the captured body, and the run later deadlocks. Probe: (review probe).
- **C04 — §9.4 capture; §9.9 substitution; §11.9 portability.** Rule now specified; today: keep/task.keep/go retain the whole available environment, so an unused Request-bearing service makes an identity callback nonportable. Probe: (review probe).
- **P13 — §7.1 rest patterns; §4.8 pattern types.** Rule now specified; today: the ready parser rejects data-rest patterns at its stage-6 gate, before enforcing the unique-known-shape requirement. The report’s union of (a,b) and (a,c) must be rejected for ambiguous shape once rest syntax is implemented. Probe: (review probe).
- **P15 — §7.4 usefulness warnings.** Rule now specified; today: the binary gives no never-used warning for the catch-all after an Int branch in f : (Int) -> Int, or for a two-position branch in an inline one-position match. Probe: (review probe).
- **EF10 — §6.8 row values; §9.4; syntax-3 §2.10.8.** Rule now specified; today: row capture and nonliteral provision are rejected at the stage-E6 parser gate, so the exact typed projection is not implemented. Probe: (review probe).
- **EF11 — §9.5 Scope lifecycle.** Rule now specified; today: i/resource exports neither the specified Scope nor scoped API; the report’s closed-scope acquisition cannot be checked against that API. Probe: (review probe).
- **SX16 — §11.8 Float text; syntax-3 §2.15.** Rule now specified; today: core.inspect(-.1.5) produces "-1.5", whose pasted expression fails Int negation typing; negative zero also needs the -. spelling. Probe: (review probe).
- **T12 — §4.4 intersections.** Rule now specified; today: the binary reports E0503 and tries to equate Int and String for Inv(Int) & Inv(String), where Inv(A) = (put = (A) -> A), rather than producing Never. Probe: (review probe).
- **T13 — §4.1 inhabitance; §7.4 coverage.** Rule now specified; today: the binary rejects passing (Never) directly to core.never with E0501, although destructuring the impossible part first succeeds; the report also finds Box(Never) and recursive Loop. Probe: (review probe).
- **T14 — §4.4 difference.** Rule now specified; today: the binary accepts a written List(A) - List(Int) and adds constraints while removing the List member; the new rule rejects the non-hole right argument before inference. Probe: (review probe).
- **T15 — §4.5 recursive variance and unused parameters.** Rule now specified; today: the binary already treats recursive-only Chain(A) as bivariant, but rejects a legal unused parameter in Phantom(A) = () with E0221 instead of retaining its specified invariance. Probe: (review probe).
- **T16 — §4.3 well-formed type applications.** Rule now specified; today: the binary accepts Bad = Thunk(1) with Thunk(N) = (run = () <- N -> Nil), and the report also infers Thunk(1) by using N as both result and need. Probe: (review probe).
- **T23 — §4.6 written polymorphic types; §4.7; syntax-3 §2.16.** Rule now specified; today: the ready parser rejects polymorphic function types inside data at the stage-7 gate, before checking their quantified subtyping or lattice operations. The new rules require monotype instantiation, rigid target checking, and preservation of quantifier boundaries. Probe: (review probe).
- **MP08 — §14.5 Budget accounting.** Rule now specified; today: current metering is inserted over lowered statements/Wasm allocation and runtime hooks; frame units include lowered locals (lower.rs budget_frame), so report depth(4000) hits the frame limit. It does not implement the specified source-node charges and one-activation frame rule. Probe: (review probe).
- **DOC1 — §7.1 keyed data patterns.** Found while writing the documentation site; today: `(name = name, age = _) = (name = "Ada", age = 36)` is refused with two E0101 diagnostics, "a key in a data pattern needs stage 6 of syntax three, which this compiler does not have yet". Reproduced by the coordinator on 9b806113.
- **DOC2 — §11.8 text form of a value of a labelled type.** The table gives `User(age = 36, name = "ada")`; today: with `ScreenPoint = (x = Int, y = Int)`, `core.inspect(ScreenPoint(x = 3, y = 4))` prints `ScreenPoint(3, 4)`: the labels are dropped. Reproduced by the coordinator on 9b806113.
- **DOC3 — §2.6.2, §9.7, §10.1.1, §10.1.2 and §B.6.1: the generated JavaScript artifact.** The standard says `i build` for the `js` and `nodejs` targets writes `name.wasm` with its generated loader `name.mjs` and `name.d.ts`, and that the module carries a target section `ilang.js`. Today three things are missing: (1) there is no generator for `name.mjs` and `name.d.ts`: `i build --target js` and `--target nodejs` write only `name.wasm` and `name.bindings.json` (a binding plan with the digest of the Wasm bytes), at both optimisation levels, and the module has no `ilang.js` section and no `target` field; (2) the built-in `@js` declaration is not implemented: the checker refuses it with E0301, "the attribute `@js` is kept for macros"; (3) a built module is therefore loaded only through the Host SDK in `bindings/javascript` (`instantiate`), which is what the repository's JavaScript tests do. The standard is not changed: the generator is to be implemented. Probe: one-file project built for both targets, 2026-11-14; `git show b4f77a273` removed an older emitter that only copied the SDK.

## A program that passes the checker and traps

State on 2026-11-14. This one is not a rule ahead of the compiler: it is a known unsound point.

- **T8/F2 — §4.7 written type parameters; §4.8 known types.** A function written `<A>(x : A) -> A` whose body gives a value of another type (the standard allows the written parameter to be relaxed) still gives callers the known type `A` of its written result. A selection that reads that known type picks the branch for the argument's type while the value has another type, and the program traps at run time (`null reference`). The review's program: `choose` with one branch for `Int` and one for `{ Int | String }`, `f = <A>(x : A) -> A { … 1 }`, and `n : Int = choose(f("s"))`. Two fixes are known. Treating written parameters as rigid closes it but rejects programs that §4.7 accepts today; it waits for the owner. Not deriving a known type from the written part of a relaxable parameter rejects nothing; it was assessed and is not implemented.
