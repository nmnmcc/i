```i run package=hello env.PORT=8080 title="src/main.i"
(
	i/process
	i/fail
	i/stdio
	std/int
)

(
	read_port
	BadPort(..)
)
BadPort = ()
read_port = () {
	int.parse(process.env("PORT")) |>
		(Ok(port) ? port > 0 && port < 65536) { port }
		| (_) { fail.raise(BadPort) }
}
main = () {
	fail.catch(read_port) |>
		(Ok(port)) { stdio.print("port " <> int.to_string(port)) }
		| (Error(_)) { stdio.print("invalid PORT") }
}
```


<p className="home-step">01 / Follow a value through a decision</p>
<h2 id="branches">Matching and overloading are one construct.</h2>
<p>The formatter has a branch for zero, another for a port, and one for a host and port together. A pipeline calls the same function. i has no keywords: <code>if</code> here is an ordinary binding.</p>

<div className="topic-copy">
<p className="home-step">02 / Provide a service, control the run</p>
<h2 id="needs">A test double uses the same need.</h2>
<p>The port reader needs the environment service. Here <code>&lt;-</code> supplies an ordinary <code>Environment</code> value whose function returns the chosen input. The reader itself is unchanged; the test does not read the process environment.</p>
<p>The checker accepts a supplied service by the same subtype rule it uses for an argument. Dependency injection and test doubles use that one rule. Raising <code>BadPort</code> adds a typed <code>Fail</code> need; catching supplies its handler.</p>
<p>That connects <a href="#branches">Functions and inference</a> to error handling. The test checks the returned result for both bad text and an out-of-range number. <a href="#tasks">Tasks</a> carry those service and error requirements too.</p>
<a className="home-text-link" href="/docs/tour/services-and-errors">Learn services and errors →</a>

<p className="home-step">03 / Keep the work’s lifetime together</p>
<h2 id="tasks">The same function can become a task.</h2>
<p>A task cannot outlive its scope. Here <code>task.both</code> joins two child calls to the port reader before returning their results. Output happens after both calls have finished.</p>
<p>The children are <a href="#branches">ordinary functions</a>. Their service needs and error types follow the same <a href="#needs">needs and error rules</a> as the first call. Concurrency keeps those requirements when the computation is composed.</p>

<h2 id="macros">Generated code keeps the type check.</h2>
<p>A typed macro declares a signature. Its call is checked against that signature, and its generated result is checked against the instantiated signature too.</p>
<p>The macro operates on the checked port value from the same program. That connects <a href="#branches">function types and inference</a> to code generation. Its implementation is a checked i function with compile-time <a href="#needs">service needs</a>, imported by the ordinary module rules.</p>
<p>The <code>.is</code> file uses i’s Lisp surface. The test calls its macro from the normal <code>.i</code> surface.</p>
