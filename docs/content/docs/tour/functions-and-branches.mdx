title: Functions and branches
description: Call function values, choose with branches, match patterns, and repeat work with recursion.

Functions turn arguments into results. Branches choose a result by matching patterns against those arguments. This page shows how calls, blocks, patterns, and pipelines fit together, so you can write choices and repeated work without control-flow keywords.

```i run package=tour title="src/main.i"
(
	i/core
	i/stdio
)

square = (x) { x * x }
main = () {
	stdio.print(
		core.inspect(square(3)),
	)
}
```

```text
9
```

`(x) { x * x }` is a function value. `square` names it, and `square(3)` calls it. The parameters and body are required; their types can be inferred. A function is a value that you can pass to another function.

## Passing a function

```i run package=tour title="src/main.i"
(
	i/core
	i/stdio
)

apply = (f, x) { f(x) }
add_two = (x) { x + 2 }

main = () {
	result = apply(add_two, 3)
	stdio.print(core.inspect(result))
}
```

```text
5
```

`apply` receives a function and calls it. The name `add_two` supplies the function value; `add_two(3)` would supply the result of calling it instead.

## Labelled arguments

```i run package=tour title="src/main.i"
(
	i/stdio
)

greet = (name, punctuation = ending) { "Hello, \(name)\(ending)" }

main = () { stdio.print(greet("Ada", punctuation = "!")) }
```

```text
Hello, Ada!
```

An argument can have a label: `punctuation = ending` receives the argument under the label `punctuation` and binds it locally as `ending`. Labels use `=`, while an annotation such as `x : Int` states a type. There are no default arguments; every argument key must be supplied.

## Blocks

```i run package=tour title="src/main.i"
(
	i/core
	i/stdio
)

main = () {
	result = {
		first = 3 + 2
		first * 2
	}
	stdio.print(core.inspect(result))
}
```

```text
10
```

A block executes its statements in order and gives the value of its final expression. The block bound to `result` therefore gives `10`. Its last statement must be an expression, rather than a binding. Braces also group a single expression. Parentheses make argument data or tuple data; they are not expression grouping.

## Choosing with branches

```i run package=tour title="src/main.i"
(
	i/core
	i/stdio
)

size = (n : Int) {
	n |> (0 | 1) { "small" } | (x ? x < 0) { "negative" } | (_) { "large" }
}
kind = (value : { Int | String }) {
	value |> (n : Int) { core.inspect(n) } | (s : String) { s }
}

main = () {
	stdio.print(
		core.inspect((size(0), size(1), size(-2), size(5))),
	)
	stdio.print(
		core.inspect((kind(7), kind("text"))),
	)
	{ 2 < 3 } |> (True) { stdio.print("yes") } | (False) { stdio.print("no") }
}
```

```text
("small", "small", "negative", "large")
("7", "text")
yes
```

`value |> (pattern) { body } | …` matches `value` against a **chain**, one function made from branches joined by `|`. A **guard** is the optional boolean condition after `?`. The match tries branches in order and takes the first matching branch whose guard succeeds. This is the language's form for choosing: there are no `if`, `else`, or `switch` keywords. For a condition, match the boolean values `True` and `False`.

`|>` passes its left value as one positional argument to the chain. Inside a parameter item, `0 | 1` gives alternative patterns; each alternative must bind the same names. A guard is tested after its pattern matches. A guarded branch does not count toward proving that every input has a branch, so `size` ends with the catch-all `_`, which accepts any value.

In the multi-branch match in `kind`, `n : Int` and `s : String` are type tests. They select the member of the incoming union and bind its value. In an ordinary single-branch parameter group, `x : Int` instead annotates the accepted argument type. Union annotations need braces, as on `value` above.

## Taking data apart

```i run package=tour title="src/main.i"
(
	i/core
	i/stdio
)

Item = (value = Int)
Empty = ()
unpack = (value : { Item | Empty }) {
	value |> (Item(value = n)) { n } | (Empty) { 0 }
}
list_parts = (xs : List(Int)) {
	xs |> ([]) { (0, []) } | ([x]) { (x, []) } | ([x, ..rest]) { (x, rest) }
}

main = () {
	pair = (4, 5)
	(a, __unused) = pair
	(left, right) = whole = pair
	stdio.print(core.inspect((a, left, right, whole)))
	stdio.print(
		core.inspect((unpack(Item(value = 8)), unpack(Empty))),
	)
	stdio.print(
		core.inspect((list_parts([]), list_parts([2]), list_parts([2, 3]))),
	)
}
```

```text
(4, 4, 5, (4, 5))
(8, 0)
((0, []), (2, []), (2, [3]))
```

A name pattern binds the matched value. A discard, either `_` or a name starting with two underscores, matches without binding a name. The tuple pattern `(a, __unused)` takes two positions from `pair` and keeps only the first.

A conjunction matches the same value with every part: `(left, right) = whole = pair` binds the two positions and also names the whole tuple.

`Item(value = n)` is a constructor pattern: it matches the constructor and takes its labelled field. `Empty` matches the constructor with no fields. Constructor patterns must use labels for labelled fields. The ordinary data pattern `(a, b)` matches a tuple of that shape.

List patterns distinguish `[]`, an exact list such as `[x]`, and a prefix with a rest such as `[x, ..rest]`. The rest is another list. `list_parts` returns the first item and the remaining list, with separate branches for empty and one-item lists. Data-rest patterns are specified in §7.1 but are not yet accepted by this compiler; list-rest patterns work as shown.

## Text, literals, and bits

```i run package=tour title="src/main.i"
(
	i/core
	i/stdio
)

prefix = (s : String) { s |> ("pre:" <> rest) { rest } | (_) { "no prefix" } }
suffix = (s : String) { s |> (rest <> ".i") { rest } | (_) { "no suffix" } }
middle = (s : String) { s |> ("[" <> rest <> "]") { rest } | (_) { "no pair" } }
literal = (x : { Int | Float | String }) {
	x |>
		(-1) { "integer" }
		| (-.1.5) { "float" }
		| ("ok") { "string" }
		| (_) { "other" }
}
packet = (bits : BitArray) {
	bits |> (<<tag, body:bits>>) { (tag, body) } | (_) { (0, <<>>) }
}

main = () {
	stdio.print(
		core.inspect((prefix("pre:a"), suffix("main.i"), middle("[b]"))),
	)
	stdio.print(
		core.inspect((literal(-1), literal(-.1.5), literal("ok"), literal(2))),
	)
	stdio.print(
		core.inspect(packet(<<7, 8, 9>>)),
	)
}
```

```text
("a", "main", "b")
("integer", "float", "string", "other")
(7, <<8, 9>>)
```

A literal pattern matches an equal value. The examples include integer, float, and string literals, including the separate negative spellings `-1` and `-.1.5`. A final discard handles the remaining values.

String patterns have one binder: `"pre:" <> rest` keeps the suffix, `rest <> ".i"` keeps the prefix, and `"[" <> rest <> "]"` keeps the middle. The fixed prefix and suffix must not overlap. Pattern strings do not interpolate expressions.

A bit-array pattern reads segments in order and must use all the bits. Here `tag` reads the first eight bits, and `body:bits` takes the rest. The catch-all handles inputs too short for the first byte. The [bit-array standard](/docs/standard/generated/chapter-8#section-8-4) defines the other formats and matching rules.

## Covering the subject

A multi-branch group, or a group with a guard, must cover every possible argument value. This module is rejected:

```i error E0516 package=tour title="src/main.i"
describe = (n : Int) { n |> (0) { "zero" } | (1) { "one" } }
main = () { describe(2) }
```

Run `i check`. The real diagnostic is **E0516**: “the clauses do not cover every value of the subject (§7.4): no clause without a guard matches `2`”. The annotation admits all integers, while the branches handle only `0` and `1`. Add an unguarded catch-all or narrow the accepted type.

A single branch without a guard has a different rule: a pattern that may fail reports failure through `Assert`, rather than being checked for exhaustive coverage. For recoverable choices, write the complete branch chain; see [services and errors](/docs/tour/services-and-errors) for the service behavior.

## Recursion

```i run package=tour title="src/main.i"
(
	i/core
	i/stdio
)

sum = (xs : List(Int), total : Int) -> Int {
	xs |> ([]) { total } | ([x, ..rest]) { sum(rest, total + x) }
}

main = () {
	stdio.print(
		core.inspect(sum([1, 2, 3], 0)),
	)
}
```

```text
6
```

Repeated work uses recursion: a function calls itself with the next values. `sum` carries its changing total as an argument, with an empty-list branch to finish the loop. Its recursive call is the last work the branch does; this is **tail position**, and the call uses no additional stack.

## Pipelines

This is `examples/tour/src/main.i`, unchanged. Its constructors build an arithmetic expression; `eval` matches each constructor and recursively evaluates its parts.

```i run package=tour title="src/main.i"
(
	i/stdio
	std/int
)

Num = (Int)

Add = (Expr, Expr)
Mul = (Expr, Expr)
Expr = Num | Add | Mul
// Inferred: (e: Expr) -> Int
eval = (e) {
	e |>
		(Num(n)) { n }
		| (Add(a, b)) { eval(a) + eval(b) }
		| (Mul(a, b)) { eval(a) * eval(b) }
}

main = () {
	sum = Add(Num(1), Num(5))
	expr = Mul(sum, Num(7))
	expr |> eval |> int.to_string |> stdio.print
}
```

```text
42
```

A pipeline passes its left value into position zero of the next call. The final line sends `expr` to `eval`, sends the integer result to `int.to_string`, and sends that string to `stdio.print`. These are ordinary function calls written in the order their results flow.

The [types page](/docs/tour/types-and-inference#inferring-the-evaluator) uses this same program to show the type inferred for `eval`.

## Operators and grouping

```i run package=tour title="src/main.i"
(
	i/core
	i/stdio
)

main = () {
	stdio.print(core.inspect(2 + 3 * 4))
	stdio.print(core.inspect({ 2 + 3 } * 4))
}
```

```text
14
20
```

Multiplication binds more tightly than addition, giving `14`; braces change the grouping to give `20`. Operators at the same precedence associate left to right. Calls and field access bind more tightly than arithmetic, and the pipeline binds less tightly. Use the [operator table](/docs/standard/generated/chapter-6#section-6-9) for the complete order.

## Current limits

The standard also allows a pattern to name the labelled parts of data, as in `(name = name, age = _)` ([§7.1](/docs/standard/generated/chapter-7#section-7-1)). The compiler on this tree refuses such a pattern with E0101; until that is fixed, read a labelled part with `.name`. Rest patterns for data (`..rest` inside `( )`) are refused in the same way; list rests work as shown above. Both differences are recorded in [the known gaps](https://github.com/nmnmcc/i/blob/main/docs/design/spec-known-gaps.md) (DOC1, P13).
