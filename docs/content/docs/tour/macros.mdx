A macro is an i function that runs in the compiler, taking code as data and returning code as data. You can use one through a normal package import, then inspect the code it produces. The test macro is a useful first example: this complete `test/example_test.i` registers a test with `std/test`.

```i test package=tour title="test/example_test.i"
(
	testlib = (test) = std/test
)
test("addition", () { assert(2 + 3 == 5) })
```

Run it in a package named `tour` with a path dependency on `std` and `[test] collection = "std/test.tests"` in `i.toml`:

```sh
i test --opt 0
```

```text
pass tour/example_test.addition
1 passed, 0 failed
```

`test` is a macro exported by the package, not a keyword. The import uses `testlib` as the module name and brings `test` into scope as a separate name. The macro creates a test function and registers it in the package's test collection. `assert` uses the assertion service supplied by the test runner. See [services and errors](/docs/tour/services-and-errors) for that distinction.

## The Lisp surface

i has two surfaces for the same core tree. Ordinary `.i` files use the syntax shown so far. `.is` files use the Lisp surface: the first item of a parenthesised form identifies the form. Module paths omit the extension, so either surface can import the other.

In the complete definition below, `(, twice)` is the exports header, `(= twice …)` binds a name, and `(-> (, value) _ …)` is a one-argument function with an inferred result. A backtick quotes code; `~value` inserts the argument's syntax into that template. Braces hold a block. Line breaks in the Lisp surface are whitespace, so the formatter may put a short definition on one line.

## A small syntax macro

Create `src/macros.is` in a package named `tour`:

```scheme file=src/macros.is title="src/macros.is"
(, twice)
(@ macro (= twice (-> (, value) _ `{(= saved ~value) (+ saved saved)})))
```

The macro inserts its argument into a binding and adds the bound value to itself. Its argument arrives as syntax, without being evaluated by the compiler as an ordinary function argument. The returned code evaluates the expression once at run time. The `@macro` attribute exists only in `.is` files; a macro is used from another module, not the module that defines it.

Use it from `src/main.i` in the same package:

```i run package=tour title="src/main.i"
(
	(Io) = i/io
	i/core
	(twice) = tour/macros
)
main = () <- (io : Io) {
	saved = 10
	io.print(
		core.inspect(twice(saved + 1)),
	)
}
```

```text
22
```

These two files form one complete example: the macro is defined in the Lisp surface and used in the normal surface.

## Inspecting the expansion

From that project directory, run the actual expansion command:

```sh
i expand --to i src/main.i
```

```text
// tour/main
(
	(Io) = i/io
	i/core
	(twice) = tour/macros
)

main = () <- (io : Io) {
	saved = 10
	io.print(
		core.inspect({
			saved = saved + 1
			saved + saved
		}),
	)
}
```

`--to i` selects the normal surface for the output. The default is `--to is`; a module containing quotations needs that surface. `--trace` also prints individual macro runs to standard error. Expansion shows the binding introduced by `twice` and the addition that replaced the call.

## Names and hygiene

**Hygiene** means generated names keep their own scope rather than accidentally capturing caller names. Here the caller and the template both bind a name spelled `saved`. The expression inserted from the caller still uses the caller's `saved`, so it computes `10 + 1`. The two references made by the template use the generated binding, giving `11 + 11`.

The expansion prints the same spelling for these names; their distinct scopes are retained in the syntax tree. The specification defines this with a fresh mark for each expansion. Code from macro arguments retains its original scope, while generated code receives the expansion's mark. References made in a template resolve in the defining module under those rules; labels are compared by text.

Macros have no host services for reading files, the network or the time. The standard requires the same result for the same inputs on every machine and places limits on each expansion. Start with a syntax macro like this one; typed macros, type queries, item generation and diagnostics have additional contracts in §14.

## The repository tour's `if` macro

The complete [`examples/tour/src/sugar.is`](https://github.com/nmnmcc/i/blob/main/examples/tour/src/sugar.is) defines `if` as a macro, rather than a language keyword. These two files are copied unchanged from the repository tour.

```scheme file=src/sugar.is title="src/sugar.is"
(, if)
(= _branches
  (-> (, then else) _ `(| (-> (, True) _ ~then) (-> (, False) _ ~else))))
(@ macro (= if (-> (, test then else) _ `(|> ~test ~(_branches then else)))))
```

```i test package=tour title="test/sugar_test.i"
(
	testlib = (test) = std/test
	sugar = (if) = tour/sugar
)

sign = (n) { if(n < 0, "negative", "not negative") }

test("if is a macro", () { assert(sign(-1) == "negative") })
```

`_branches` makes a two-branch function that matches `True` or `False`. The `if` template pipes the test expression into those branches. The branch expressions remain code until the selected branch runs. The test imports the macro from `tour/sugar` and uses it inside `sign`, just as it uses `test` from `std/test`.
