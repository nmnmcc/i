Concurrency in i is structured: a task lives inside the block that starts it. This page shows starting children, joining results, and handling child failure after cleanup. The examples print only after the relevant work finishes, so their output does not depend on which task runs first.

```i run package=tour title="src/main.i"
(
	i/task
	i/core
	(Io) = i/io
)
main = () <- (io : Io) {
	answer = task.scope((s) {
		first = task.go(s, () { 20 })
		second = task.go(s, () { 22 })
		task.join(first) + task.join(second)
	})
	io.print(core.inspect(answer))
}
```

```text
42
```

## Start and join

`task.scope` calls its body with a scope handle. `task.go(scope, body)` starts a child in that scope and returns a `Task` handle. `task.join(handle)` waits for its result. Here the children compute independently, and the parent adds their joined values. The scope cannot return while either child remains live.

A scope also waits for children that its body did not explicitly join. Joining is useful when you need a child's result before proceeding; automatic waiting establishes the lifetime boundary even when no result is needed. Returning a task handle does not extend that lifetime or make a later join valid.

The program entry already runs inside a task run with a scheduler. `task.run` creates an explicit nested run when needed; this example needs only a scope. Tasks and schedulers are library facilities built using services and control operations. You import `i/task` and call its functions through the same module rules as other libraries.

`Task(A, E)` carries a result type and an error type. Joining returns `A` or raises an error through `Fail(E)`. It does not return a `Result`; wrap a computation in `fail.catch` when you want one, as on the [services and errors](/docs/tour/services-and-errors) page.

## Combining results

For independent computations, `task.both` joins two children and returns their results as a pair. `task.map_concurrently` starts a child for each input and returns the results in input order:

```i run package=tour title="src/main.i"
(
	i/task
	i/core
	(Io) = i/io
)
main = () <- (io : Io) {
	values = task.map_concurrently([3, 1, 2], (n) { n * 10 })
	io.print(core.inspect(values))
	io.print(
		core.inspect(task.both(() { 7 }, () { "eight" })),
	)
}
```

```text
[30, 10, 20]
(7, "eight")
```

The input order is `3, 1, 2`, so the output is `30, 10, 20`, regardless of completion order. The pair also preserves argument order. This is a useful way to keep concurrent computation separate from ordered output.

Scheduling order is not fixed. Prints inside separate children, competing sends, and the winner of `task.race` can differ across runs. A race cancels its loser and waits for its cleanup; an observed failure before success commits fails the scope. It is not a search for a successful result that ignores earlier failures.

## Failure cancels the scope

When a scope body or child raises an error, the scope cancels its body and children, waits for their finals, and raises the chosen error. If several tasks actually fail, the specification chooses the failure with the least task path; cancellation itself is not a failure.

```i run package=tour title="src/main.i"
(
	i/task
	i/resource
	i/fail
	i/core
	(Io) = i/io
)
main = () <- (io : Io) {
	state = task.ref(0)
	answer = fail.catch(() {
		task.scope((s) {
			ready : task.Channel(Nil) = task.channel()
			task.go(s, () {
				resource.ensure(
					() {
						task.send(ready, Nil)
						task.sync(task.never())
					},
					() { task.update(state, (n) { (n + 1, Nil) }) },
				)
			})
			task.receive(ready)
			task.go(s, () { fail.raise("child failed") })
			Nil
		})
	})
	io.print(core.inspect(answer))
	io.print(
		core.inspect(task.update(state, (n) { (n, n) })),
	)
}
```

```text
Error("child failed")
1
```

The first child installs a final and sends a readiness message over a channel. Channels are unbuffered: send and receive rendezvous. Only after that handshake does the parent start the failing child. The first child then waits on an event that never becomes ready. Failure cancels that wait and runs its final.

The final increments scheduler-owned state through `task.update`. Every value and binding remains immutable: `state` is an immutable handle to that state. The callback returns the new stored value and the result of the update. The parent reads the counter after the scope has unwound, proving the final finished once before the catch returned.

Cancellation is delivered at a task's next scheduler suspension. A child that has not started is dropped without running its body. An already-running final is shielded from a second cancellation, and the scope waits for it; a final that waits forever can keep cancellation waiting forever. A stop is not caught and does not offer this cleanup guarantee.

## Workers

The standard permits tasks to run on multiple workers, using multiple cores. The host chooses the worker count; task code does not observe which worker executes it. Results correspond to some serial order of task steps, but that order can change between runs and worker counts.

Portable values may cross workers. Ordinary scopes check child results and errors for portability; local scopes support values that must stay on their worker. No public task-starting operation detaches work from its owning scope. The examples use integers, strings and ordinary data and do not depend on worker assignment.
