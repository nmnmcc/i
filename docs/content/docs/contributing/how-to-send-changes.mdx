## A first change

Choose the relevant [standard](/docs/standard) paragraph. For language changes, edit that text first, add a distinct case beside a related one, then implement it. Give the new case an unused, descriptive basename; discovery is recursive and needs no registration list.

Keep `spec:` and `expect:` at the top. Other expectations are `compile-error` or `warning` with the actual diagnostic code, and `stop` with its first message line; `at:` checks further stop lines, and `output:` checks emitted text. Package cases use `#` headers in `i.toml`.

## Focused checks

The filtered command for the existing case is `cargo test -p ilang-cli --test spec --locked -- a1_entry_exports`; substitute your new basename. [The runner](https://github.com/nmnmcc/i/blob/main/crates/ilang-cli/tests/spec.rs) checks each header at O0/O2 and compares the levels. [Building and testing](/docs/contributing/building-and-testing) gives setup, the CLI build command, and the shared heavy-queue requirement.

## Library cases

```i test stdout=exact package=changes title="test/bool_test.i"
(
	testlib = (test) = i/test
	i/bool
)

test("negation", () { assert(bool.not(False()) == True()) })
```

```text
pass changes/bool_test.negation
1 passed, 0 failed
```

Use the filter shown on [building and testing](/docs/contributing/building-and-testing#filtered-tests) to run an existing library case; filters select test names, without making package checking module-local. Widen the checks to the changed layer, source formatting, compiler lint, snippets, and any affected docs or editor checks.

## Corpus effects

A language change includes its spec text, `tests/spec` case, and an account of its effect on `tests/review`. Recorded output is an observation; O0/O2 agreement can preserve a shared defect. Change expectations only with the requiring spec paragraph, review the separate semantic requirement, and promote fixed known failures. [The testing guide](https://github.com/nmnmcc/i/blob/main/docs/testing.md) documents deliberate regeneration.

## Submission

A branch must be up to date with `main` before it can merge; branch protection refuses the merge otherwise. Two branches that are each green can still fail together: one may use a form the other changed, as when a language change and a new library module written in the old form merge in either order. Sync before merging (`git merge origin/main`, or rebase) and run `i check --project stdlib`, which catches a language change that reaches the standard library.

Before merging, confirm that the head commit of the pull request has one complete, successful run. Do not put `[skip ci]` on a pull request head: it starts no run, but it enters the same concurrency group and cancels the run that was still going, so the merged tree is never checked by the full gate. To add documentation, rebase it into the code commit or accept one new complete run.

Do not commit acceptance reports, proofs or run logs; keep them in the pull request description or git history.

Use a plain English commit subject describing the change, following recent commits. The [README](https://github.com/nmnmcc/i/blob/main/README.md) and [development guide](https://github.com/nmnmcc/i/blob/main/docs/development.md) describe checks but provide no submission procedure; ask through the [issue tracker](https://github.com/nmnmcc/i/issues) for `nmnmcc/i`.

[Compiler architecture](/docs/contributing/compiler-architecture) identifies implementation entry points.

## Known external flakes

The Nix cache proxy sometimes answers `HTTP error 418`, or the GitHub cache API
rate limits it (`ResourceExhausted`, `rate limit exceeded`); FlakeHub prints
`Cannot find netrc` when it is not configured. A run that fails only with one
of those messages is an infrastructure failure, not a change failure: rerun the
job, or run the same command locally.

The check steps go through `scripts/ci/retry-on`, which retries **only** those
signatures, at most twice with a 30 s backoff. Every retry prints a warning and
the job summary ends with the number of retries, so a gate that passes only by
retrying is visible. Any other failure is returned unchanged and never retried.

If this happens more than ten times in a month, stop retrying and change the
dependency (for example, do not install the cache proxy in jobs that do not
need it). The retry count in the job summary is the evidence for that decision.
